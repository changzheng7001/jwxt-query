# 原站页适配：试错记录与当前状态

> 最后更新：V222（0.9.40，诊断版）

## 一、目标

「原站」按钮打开的教务系统页面，要做到：
1. 与手机浏览器打开的效果一致
2. 布局不被污染、左右两侧内容与左侧菜单完整可见
3. 状态栏位置一条固定黑条作为边界（不随网页变化）

## 二、页面结构的硬事实

- 按钮指向 `https://jwxt.cicp.edu.cn/jsxsd/framework/xsMainV.htmlx?native=1`
- 这是**外壳页**：左侧 `.sidebar`（宽 275px）+ 右侧 `<iframe src="/jsxsd/framework/xsMainV_new.htmlx?t1=1">`
- 外壳页**不是 frameset**，移动/桌面 UA 返回内容完全相同
- 页面设计宽度约 **1042px**，自带 `<meta name="viewport" content="width=device-width">`（共 2 个）
- 外壳页 **没有** `@media`、没有反嵌入（frame busting）代码、没有顶层跳转代码
- 在 390 视口下，Chrome 里 `.sidebar` 是 `display:block`、可见的；**页面不会自己收栏**
- 个人中心页 `xsMainV_new.htmlx` 本身没有左侧导航，侧栏只能来自外壳页 —— 所以 URL 必须停在外壳页

## 三、已经踩过的坑（每条都实测过）

| 做法 | 结果 | 原因 |
|---|---|---|
| `body{min-width:1240px}` | 用户否决 | 靠横滑，不是要的效果 |
| `width=1200,initial-scale=0.33` | 只露左上角 | initial-scale 与页面自带 viewport 冲突，实际得 0.985 |
| 完全零注入（V214/V217） | 版面铺开、只露左侧 | WebView 不会按 device-width 自动 fit，必须接管缩放 |
| `setInitialScale(37)` 配合删 viewport | 无变化 | 被后续某次 fit 覆盖 |
| 顶部白条/底部地址栏 | 用户强烈否决 | 要的是状态栏位置的黑条，不是浏览器 UI |
| `nativeUntil` 写成 `static` | **全局污染** | 打开原站页后 120 秒内所有页面都被当原站页处理 |
| 留白加在 WebView 自身 padding | 顶部被裁半个字 | padding 管不住 `position:fixed` 头部 |
| 父容器四边 padding | 侧栏被收 | padding 改变了视口宽度，页面响应式收栏 |

## 四、当前有效方案（V218 起）

### 4.1 视口：钉死 1042，不随设备变
```java
return fetch(url, nativeInsetStyle(), true);   // 摘掉页面自带 viewport，再注入
```
```html
<meta name="viewport" content="width=1042,initial-scale=0.374,maximum-scale=3,user-scalable=yes">
```
配套侧栏保活（只作用于外壳页）：
```css
.sidebar{display:block!important;width:275px!important;position:relative!important;}
```
要点：**版面宽度不能变**。一变窄，页面响应式就把侧栏收掉 —— 这就是"先有侧栏、一秒后没了"的根因。

### 4.2 缩放：首帧锁死
```java
ws.setTextZoom(100);                 // 固定文字缩放，系统字体大小不影响布局
ws.setLoadWithOverviewMode(false);   // 关闭加载完成后按内容宽度重新 fit
```
`overview=true` 会在 iframe 撑开之后重算比例、覆盖 initial-scale，表现为"跳一下、校徽突然变大"。

### 4.3 留白：只上下，不左右
```java
parentB.setPadding(0, stripH, 0, gbH);   // 左右必须为 0
```

### 4.4 黑条
- 40dp 高、`0xFF000000`、铺在 decorView 顶部
- 离开原站页要摘掉。**关键判据是 WebView 是否可见**：
```java
if (w.getVisibility() != View.VISIBLE || ...) 摘掉
```
> 反面教材：`final WebView w = webViewOf(act)` 说明 WebView 是**复用的同一个**，
> 返回改造页面时它只是被 `setVisibility(GONE)` 隐藏，`getUrl()` 仍停在原站页地址。
> 所以任何只看 URL 的移除逻辑都会失效（V219/V220 就栽在这里）。

## 五、截至目前仍未通过验收的三点

1. 打开后仍会出现"跳一下、左上角校徽变大"
2. 退回改造页面时黑条不消失（偶尔在 App 页面闪一下）
3. 侧栏虽稳，但仍有一次跳动

## 六、V222 诊断版怎么用

屏幕上左下角会出现一个小黑块，实时显示：
```
scale=0.374  size=1042x600  vis=Y
/jsxsd/framework/xsMainV.htmlx?native=1
```
- `scale`：WebView 当前缩放比例。**跳变前后这两个数字的差值就是答案**
- `size`：WebView 控件尺寸
- `vis`：WebView 是否可见（Y/N），用于判断黑条为什么没摘

打开原站页 → 等它"变样" → 截图。对比跳变前后的 `scale`：
- 若 `scale` 变了 → 是 WebView 在改比例（继续在外层找第二处 fit）
- 若 `scale` 不变而画面变了 → 是页面自己在改布局（要去外壳页脚本里找）

## 七、如果还要继续查，优先级建议

1. `CookieWebClient` 里 `shouldInterceptRequest` 对 iframe 子 frame 的处理，是否导致子 frame 二次触发 viewport 协商
2. 外壳页 JS 是否有基于 `window.innerWidth` 的布局分支（虽然静态扫描没发现 `@media`，但可能有内联判断）
3. MainActivity（只有 smali）里是否有 `onPageFinished` / `onResize` 触发的 `zoomIn/zoomOut`
